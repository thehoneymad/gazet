Cascade Design

Chapter 1

Cascade: Component-Aware Geocoding with Hierarchical Address Validation

Abstract

We present Cascade, a geocoder and address validation engine that extends traditional geocoding architectures with component-aware processing and graduated hierarchy penalties. Cascade builds upon the proven Carmen geocoder architecture while introducing three key innovations: (1) component-aware text processing that classifies address elements by type during phrase generation, (2) S2 spatial indexing that replaces Morton encoding with hierarchical cell structures better suited for administrative boundaries, and (3) ranged address feature support that enables single features to represent entire address ranges with interpolation capabilities. Our system maintains sub-second query performance while providing enhanced address validation through graduated hierarchy penalties (0.05, 0.15, 0.25) that encourage complete address hierarchies over partial matches. Cascade demonstrates that targeted architectural enhancements can significantly improve geocoding accuracy without sacrificing the performance characteristics that make Carmen suitable for production deployment.

1. Introduction

1.1 Problem Statement

Modern geocoding systems must convert textual address queries into precise geographic coordinates while handling variations in spelling, abbreviations, incomplete addresses, and multiple languages. The challenge extends beyond simple text matching to include address validation, hierarchy completion, and coordinate interpolation for ranged address features. Existing geocoding systems like Carmen provide robust text processing and spatial indexing but lack component-aware processing that can distinguish between different types of address elements and apply appropriate validation rules.

Traditional geocoding approaches treat all address components uniformly during text processing, leading to suboptimal matching when queries contain incomplete hierarchies or when validation requires understanding the semantic relationships between address elements. For example, a query matching "Main Street" with "Washington" (state) should receive lower relevance than one matching "Main Street" with "Seattle" (city) due to the missing intermediate administrative level.

1.2 Contributions

This paper presents Cascade, a geocoding architecture that addresses these limitations through three primary contributions:

  1. Component-Aware Processing Pipeline: We introduce a classification system that identifies address element types (house numbers, street names, administrative regions, address ranges) during text processing, enabling component-specific matching strategies and validation rules.

  2. Hierarchical Penalty System: We develop a graduated penalty mechanism that applies increasing relevance reductions (0.05, 0.15, 0.25) based on the number of missing administrative levels between matched components, encouraging complete address hierarchies.

  3. Ranged Address Feature Support: We implement comprehensive support for address ranges using USPS ZIP+4 dataset structures, enabling single features to represent entire address ranges with precise coordinate interpolation for individual addresses within ranges.

1.3 System Overview

Cascade maintains Carmen's proven three-layer architecture while adding targeted enhancements at each layer. The text processing layer incorporates component classification as a post-processing step that preserves performance while adding semantic understanding. The spatial indexing layer replaces Morton encoding with S2 Level 16 cells that provide hierarchical spatial organization better suited for administrative boundary relationships. The feature storage layer extends the CarmenSource interface to support integrated geocode storage and ranged address metadata.

2. Background and Related Work

2.1 Carmen Geocoder Architecture

Carmen established the foundational three-layer architecture that separates text processing, spatial indexing, and feature storage concerns. The text processing layer transforms raw feature text through a five-stage pipeline: text extraction from feature properties, tokenization with comprehensive normalization, token replacement through global and regex-based rules, phrase generation creating all contiguous token combinations, and relevance calculation using batch-local frequency analysis.

The spatial indexing layer maps phrase IDs to geographic coordinates using Morton-encoded grid systems stored in RocksDB. Morton encoding converts 2D coordinates into single integers that preserve spatial locality through Z-order curve properties, enabling efficient range queries for rectangular bounding boxes. The GridStore implementation provides streaming spatial queries with MinMaxHeap priority queues for result management.

The feature storage layer abstracts storage through the CarmenSource interface, supporting pluggable backends including memory storage for testing, MBTiles for SQLite-based storage, and S3 for cloud deployment. Features are distributed across shards using modulo arithmetic (feature_id % 2^24) for balanced load distribution and concurrent access patterns.

2.2 Limitations of Existing Approaches

Carmen's uniform text processing treats all address components identically, preventing component-specific validation and matching strategies. The system applies a fixed 0.01 hierarchy gap penalty regardless of the administrative distance between matched components, providing insufficient granularity for address validation. Morton encoding, while effective for general spatial queries, lacks the hierarchical properties needed for administrative boundary relationships.

Address processing in Carmen occurs across multiple disconnected stages without comprehensive range support. Address recognition happens during tokenization, permutation generation during phrase matching, and coordinate calculation during verification, but the system lacks integrated support for address ranges that span multiple individual addresses.

Component classification uses pattern recognition and contextual analysis to identify address element types. House numbers are identified through numeric patterns with optional alphabetic suffixes like "123A". Street names are recognized after removing directional prefixes ("North Main Street" → "Main Street") and street type suffixes ("Main Street" → "Main"). Administrative regions are classified through gazetteer lookup and boundary validation. Address ranges are identified through range pattern recognition including house number ranges with parity indicators ("100-198 Even"), ZIP+4 extensions ("98101-1001 to 98101-1050"), and secondary address ranges ("Apt 1-24").

The system handles intersection processing through dedicated intersection phrase generation with "+intersection" prefixes, enabling queries like "Oak and Main" to match intersection features. CJK text processing splits Chinese, Japanese, and Korean ideographs into individual characters to enable address parsing for languages that do not use spaces between address components.

The classification process generates component type metadata that flows through the spatial indexing layer attached to grid entries. This metadata enables hierarchy validation during spatial stacking and supports component-specific matching strategies during query processing.

3.3 S2 Spatial Indexing with Hierarchical Properties

Cascade replaces Morton encoding with S2 Level 16 cells that provide hierarchical spatial organization better suited for administrative boundary relationships. S2 cells offer several advantages over Morton encoding: global coverage without projection distortion, hierarchical cell structure that naturally represents administrative boundaries, and Hilbert curve ordering that preserves spatial locality while providing better clustering properties for administrative regions.

S2 Level 16 cells provide approximately 150-meter resolution equivalent to Carmen's zoom 16 grid system while offering superior spatial clustering through the S2 hierarchy. For example, an address at coordinates (47.6062, -122.3321) in Seattle becomes S2 cell ID 6093613931042816000, enabling efficient range queries over rectangular regions while maintaining spatial locality.

The GridStore implementation extends Carmen's approach with component type metadata attached to grid entries. Each entry includes standard relevance and score information along with component type classifications that enable hierarchy validation during spatial stacking operations. The storage uses a three-level hierarchy: PhraseRecord structures contain arrays of RelevScore entries grouped by relevance and score combinations, each RelevScore points to arrays of Coord structures representing all S2 cells with that relevance-score combination, and each Coord stores an S2 cell ID and points to arrays of feature IDs at that location with component type metadata.

The spatial stacking algorithm combines grid entries that overlap spatially to build complete addresses. When a query matches "Main Street" and "Seattle", the algorithm finds grid entries for both phrases and checks if their S2 cells overlap within the same or adjacent grid cells. Overlapping entries stack together with combined relevance scores, while non-overlapping entries remain as separate results with lower relevance. Component type compatibility prevents inappropriate stacking - house numbers cannot stack with country-level components due to extreme hierarchy gaps and spatial scale mismatches.

3.4 Graduated Hierarchy Penalty System

The hierarchical penalty system calculates graduated penalties based on missing administrative levels between matched components. The system operates during spatial stacking when grid entries from multiple phrases are combined based on S2 cell overlap.

Penalty calculation considers the administrative distance between matched components:

  • Complete hierarchy (street + city): No penalty (0.00)
  • Missing 1 level (street + state, missing city): Light penalty (0.05)
  • Missing 2 levels (street + country, missing city + state): Medium penalty (0.15)
  • Missing 3+ levels: Heavy penalty (0.25)

4. Ranged Address Feature Processing

4.1 Range Recognition and Classification

Cascade implements comprehensive support for ranged address features that represent entire address ranges within single features. The system recognizes address ranges during component classification through pattern analysis that identifies house number ranges with parity indicators, ZIP+4 extension ranges, and secondary address ranges for multi-unit buildings.

Range patterns include primary address ranges (100-198 Main Street), ZIP+4 ranges (98101-1001 through 98101-1050), and secondary address ranges (Apt 1-24, Suite 100-150). The classification process maintains relationships between primary and secondary ranges within the same feature, enabling comprehensive address validation for complex multi-unit buildings.

4.2 Range-Aware Phrase Generation

The phrase generation process creates searchable terms for both complete address ranges and individual addresses within range boundaries. A ranged feature generates phrases for the street name, the full range designation, and individual addresses that fall within the range boundaries according to parity constraints.

For a feature representing "100-198 Main Street" with even parity, the system generates phrases for "main street", "100 main street", "102 main street", continuing through "198 main street" for all even-numbered addresses. This enables queries for specific addresses within the range to match the ranged feature while maintaining efficient storage through single-feature representation.

4.3 Spatial Indexing with Range Metadata

Ranged address features are indexed using S2 cells that cover the geographic extent of the address range. LineString geometries representing street segments are converted to S2 cell coverings that encompass the entire range, while individual address points within the range are indexed at their specific S2 cell locations.

Range metadata includes address boundaries (low and high values), parity constraints (odd, even, or both), secondary address ranges for multi-unit buildings, and LineString geometries for coordinate interpolation. This metadata enables the spatial matching process to determine whether a query address falls within a stored range and supports precise coordinate calculation through interpolation.

4.4 Address Interpolation and Coordinate Resolution

Address interpolation calculates precise coordinates for specific addresses within ranged features using LineString geometries and proportional positioning. The interpolation process determines the proportional position of the query address within the range and calculates coordinates along the LineString geometry.

For a query address "150 Main Street" matching a range "100-198 Main Street", the system calculates that 150 represents the midpoint of the range and returns coordinates at the midpoint of the associated LineString geometry. Parity constraints ensure that only valid addresses within the range receive interpolated coordinates, preventing invalid addresses like odd numbers in even-parity ranges.

Phase 4 (Context Building) uses administrative hierarchy relationships to fill missing hierarchical components, with component type metadata guiding the gap-filling process and penalty calculation based on the success of hierarchy completion.

House numbers and ZIP codes remain language-neutral as numeric components.

The system maintains language-specific pattern libraries for each component type, adapting classification rules to language-specific address formatting conventions. Range pattern recognition adjusts to language-specific formatting while maintaining consistent numeric ranges and interpolation geometry across language variants.

6. Implementation Details

6.1 Storage Architecture and Streaming Query Processing

Cascade implements the CascadeSource interface that extends Carmen's CarmenSource with geocode integration capabilities. The interface supports established storage backends (memory, MBTiles, S3) while adding support for integrated address and coordinate storage when geocodes are provided with address data.

The streaming query processing uses MinMaxHeap priority queues for efficient result management. The system retrieves database entries matching phrase ID ranges, decodes grid entries on-demand with component type filtering, and maintains top results sorted by relevance and spatial distance. For example, a query for "Main Street" retrieves all phrase IDs matching street name patterns, then streams through grid entries to find spatially coherent matches while filtering by component type compatibility.

Feature storage maintains the full GeoJSON feature document including geometry, text properties, metadata, and integrated geocodes. Stored properties include address text and language variants for display ("Main Street" / "Calle Principal"), coordinate centroids for feature location, relevance scores for ranking, component types for classification (STREET_NAME, HOUSE_NUMBER, ADMINISTRATIVE_REGION), and address-related properties including ranged address data with house number ranges ("100-198"), parity indicators ("Even"), ZIP+4 extensions ("98101-1001 to 98101-1050"), and secondary address ranges ("Apt 1-24").

6.2 Database Schema and Encoding

The spatial indexing layer uses composite keys that enable efficient range queries and language filtering. Each key contains a 1-byte type marker (0 for exact phrases like "main street", 1 for prefix bins covering phrase ID ranges), a 4-byte phrase ID supporting up to 4 billion phrases, and a variable-length language bitfield supporting 128 languages with optimized encoding for common cases where empty arrays represent universal language support.

GridEntry structures extend Carmen's approach with component type metadata alongside standard relevance, score, and feature ID information. S2 cell IDs replace Morton codes as spatial identifiers, providing hierarchical spatial organization that supports administrative boundary relationships and graduated penalty calculation. For example, a street address "123 Main Street" stores its S2 cell ID (6093613931042816000), component type (HOUSE_NUMBER + STREET_NAME), relevance score (0.9), and feature ID for complete document retrieval.

6.3 Performance Optimizations and Address Validation Workflow

Cascade maintains Carmen's performance optimizations while adding component-aware enhancements. Batch-local relevance calculation provides coarse filtering during spatial matching, with early termination algorithms preventing examination of low-relevance matches when the relevance difference exceeds 0.25 points. For example, if the top result has relevance 0.9, the system stops processing entries with relevance below 0.65.

7. Evaluation Framework

7.1 Performance Metrics

Cascade evaluation focuses on three primary metrics: query response time compared to Carmen baseline, storage efficiency for ranged address features versus individual address points, and accuracy improvements through component-aware processing and graduated hierarchy penalties.

Query performance evaluation measures end-to-end response times for representative address queries across different complexity levels: simple address queries (house number + street), partial hierarchy queries (street + state, missing city), and complex range queries (specific address within stored range). Storage efficiency compares space requirements for ranged features versus equivalent individual address representations.

7.2 Accuracy Assessment

Address validation accuracy assessment evaluates the effectiveness of component-aware processing and graduated hierarchy penalties in producing more relevant results. Test cases include incomplete address hierarchies where graduated penalties should improve ranking, cross-administrative boundary queries where component type validation should prevent inappropriate matches, and ranged address queries where interpolation should provide precise coordinates.

The evaluation framework compares Cascade results against Carmen baseline using standardized address datasets with known ground truth coordinates and administrative hierarchies. Accuracy metrics include ranking quality for incomplete hierarchies, coordinate precision for interpolated addresses, and false positive rates for cross-boundary matches.

8. Discussion and Future Work

8.1 Architectural Trade-offs

Cascade's component-aware approach introduces additional complexity in exchange for improved address validation capabilities. The post-processing classification step adds minimal overhead to the text processing pipeline while enabling significant improvements in result quality through component-specific matching strategies.

The transition from Morton encoding to S2 spatial indexing provides hierarchical properties that support administrative boundary relationships at the cost of increased implementation complexity. However, the S2 hierarchy enables more sophisticated spatial queries and better support for administrative containment relationships.

8.2 Scalability Considerations

Cascade maintains Carmen's scalability characteristics through careful preservation of the three-layer architecture and established performance optimizations. Component type metadata adds minimal storage overhead while enabling significant improvements in query accuracy through better understanding of address element relationships.

Ranged address features provide storage efficiency improvements for datasets with extensive address ranges, reducing storage requirements compared to individual address point representations while maintaining query performance through efficient S2 cell indexing.

8.3 Future Enhancements

Future work includes expanding component classification to support additional address formats and international addressing standards, implementing machine learning approaches for improved component type detection, and developing adaptive penalty systems that adjust based on regional addressing conventions.

Additional research directions include integration with real-time address validation services, support for temporal address changes through versioned feature storage, and optimization of S2 cell level selection based on administrative boundary characteristics and query patterns.

9. Conclusion

Cascade demonstrates that targeted architectural enhancements can significantly improve geocoding accuracy while preserving the performance characteristics that make systems suitable for production deployment. The component-aware processing pipeline, graduated hierarchy penalty system, and ranged address feature support address key limitations in existing geocoding architectures without requiring fundamental changes to the proven three-layer approach.

The system's ability to maintain sub-second query performance while providing enhanced address validation through semantic understanding of address element relationships represents a significant advancement in geocoding technology. Cascade's architecture provides a foundation for future research in component-aware geocoding and hierarchical address validation systems.

By building upon Carmen's established architecture while introducing targeted innovations, Cascade achieves the dual goals of improved accuracy and maintained performance, demonstrating that evolutionary architectural improvements can deliver significant benefits without sacrificing operational characteristics essential for production geocoding systems.

Appendix A: Performance Optimization Specifications

A.1 Batch-Local Relevance Calculation

Cascade implements batch-local frequency analysis following Carmen's approach where relevance scores are calculated within each indexing batch rather than globally across the entire dataset. The generateFrequency function counts token occurrences only within the current batch of documents being indexed using the formula Math.log(1 + totalfreq / termfreq).

This batch-local approach creates intentionally inconsistent relevance scores across different indexing operations but serves as an effective coarse filter during spatial matching before expensive query-time processing begins.

A.2 Early Termination Algorithms

The coalescing algorithm implements early termination when max_relevance - grid_entry.relev >= 0.25, preventing examination of millions of low-relevance matches. Grid entries are sorted by relevance and only results within 0.25 relevance points of the maximum are considered for further processing.

A.3 Streaming Query Processing

Spatial queries use MinMaxHeap priority queues for efficient result management. The streaming query function retrieves database entries matching phrase ID ranges, decodes grid entries on-demand, and maintains top results sorted by relevance and spatial distance.

A.4 Prefix Binning Optimization

Range queries over large phrase ID ranges use prefix binning with type marker 1 to create aggregated database entries. Bin boundaries are stored in a special "~BOUNDS" database entry containing packed 4-byte integers defining phrase ID ranges for each bin.

Appendix B: Complete Indexing API Specification

B.1 Function Signatures

The indexing interface provides the update function as the primary entry point with parameters for source (CascadeSource instance), docs (Array of GeoJSON Feature documents), options (zoom level and optional token replacements), and callback for completion notification.

B.2 Required GeoJSON Properties

Each feature document must include: id (unique feature identifier), carmen:text (primary feature name for indexing), carmen:center (longitude, latitude coordinate array), geometry (valid GeoJSON geometry object), and optional carmen:score (relevance score 0-1000).

B.3 Batch Processing Mechanics

Features are processed in batches with coordinated phrase insertion and grid mapping: generate phrases from feature text with component classification, insert phrases into fuzzy-phrase builder to obtain temporary phrase IDs, store phrase ID to S2 cell mappings in GridStore builder with component metadata, and finalize index by renumbering phrase IDs and writing structures to disk.

B.4 Storage Finalization Process

The store function coordinates final ID assignment and disk persistence by finishing the fuzzy-phrase builder to obtain ID mapping, renumbering GridStore entries using the mapping, and writing both fuzzy-phrase and GridStore data to their respective storage locations.

Appendix C: Extended Address Processing Specifications

C.1 Address Format Pattern Recognition

Cascade recognizes five distinct address format patterns extending Carmen's approach: standard numeric addresses (10, 10a), range addresses (10-19, 10-19a), directional Kane County Illinois style (6N23), directional Waukesha County Wisconsin style (W350N5337, N453), and Russian addresses with korpus and stroenie suffixes.

C.2 Address Permutation Generation

During query processing, address indexes receive special handling through numTokenize masking that replaces numbers with hash symbols and addressPermutations filtering that keeps only valid address patterns to prevent non-address matches from contaminating address search results.

C.3 Address Context Tracking

The system maintains address context through structured objects containing the actual address number from the query, the position indicating whether the number appears first or last in the phrase, and the token position within the original query for coordinate mapping.

C.4 Interpolation Property Specification

Address interpolation uses six standardized properties for LineString geometry processing: left side from/to house numbers (carmen:lfromhn, carmen:ltohn), right side from/to house numbers (carmen:rfromhn, carmen:rtohn), and left/right side parity indicators (carmen:parityl, carmen:parityr) specifying Even, Odd, or Both address patterns.

Appendix D: Multi-Zoom Coordination Algorithms

D.1 Coordinate Scaling Between Zoom Levels

The adjust_bbox_zoom function converts coordinates between zoom levels using bit shifting operations where zooming in multiplies coordinates by 2^(zoom_difference) and zooming out divides by 2^(zoom_difference) with appropriate edge adjustment for boundary conditions.

D.2 Compatible Zoom Level Detection

The coalescing process identifies compatible zoom levels for hierarchical matching by checking that the absolute difference between zoom levels does not exceed the maximum allowed zoom difference threshold, enabling features from different zoom levels to stack appropriately.

D.3 Distance Calculation Formulas

Spatial distance calculations use zoom-aware conversion ratios through tiles_per_mile_by_zoom which provides pre-calculated conversion factors, and scoredist which combines spatial distance with feature scores using exponential weighting to balance proximity and importance.

Appendix E: Storage Implementation Details

E.1 Shard Calculation Formula

Feature distribution uses modulo arithmetic for balanced sharding where the shard number is calculated as the absolute value of the integer feature ID modulo 2^24, supporting up to 16,777,216 possible shards for distributed storage and efficient retrieval.

E.2 File Naming Conventions

Storage files follow standardized naming patterns where fuzzy-phrase data is stored in {source_basename}.fuzzy/ directory, GridStore data in {source_basename}.gridstore.rocksdb/ directory, and feature storage in {source_basename}.mbtiles or custom backend format.

E.3 Database Schema Encoding

GridStore uses composite keys with precise byte layouts including 1-byte type marker (0 for exact phrases, 1 for prefix bins), 4-byte big-endian phrase identifier supporting up to 4 billion phrases, and variable-length language bitfield supporting 128 languages with optimized encoding for common cases.

Value encoding uses hierarchical compression with GridEntry structures containing quantized relevance (2-bit values representing 0.4, 0.6, 0.8, 1.0), 8-bit importance scores (0-255), S2 Level 16 cell identifiers, feature IDs truncated to 24 bits, source phrase hashes, and component type classifications.

Appendix F: Query Processing Mechanics

F.1 Bitmask Token Coverage Tracking

Phrase matching uses bitmasks to track which query tokens each phrase covers, enabling efficient determination of phrase completeness and overlap detection during spatial stacking operations.

F.2 S2 Cell Range Queries

Bounding box spatial matching uses S2 covering algorithms to convert rectangular regions into sets of S2 cells that completely cover the query area, balancing query efficiency with storage overhead by selecting appropriate cell levels.

F.3 Language Filtering Operations

Multi-language support uses bitwise operations for efficient filtering where empty language arrays match all languages and specific language bits must overlap between stored features and query language preferences for successful matches.

F.4 Context Building Integration

Administrative hierarchy completion uses spatial containment queries to identify missing hierarchical components, attempting to fill gaps using boundary containment and administrative relationships with confidence-based penalty adjustments for uncertain boundary relationships.
